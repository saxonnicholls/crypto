Detailed Description

X25519 (RFC 7748): Diffie-Hellman on Curve25519 with the Montgomery ladder.

Overview

Key agreement: each side has a 32-byte secret, publishes public_key_from_secret(secret), and computes shared_secret(own secret, peer's public key); both get the same 32 bytes, which are input to a KDF, never a key themselves. scalar_mult is RFC 7748's X25519 function itself, for the test vectors and for protocols that define their own checks.

RFC 7748's rules, as implemented:

  • The secret is clamped (clamp: bits 0, 1, 2 and 255 cleared, bit 254 set) inside every call: callers pass 32 uniformly random bytes or KDF output as they are.
  • The peer's u-coordinate is decoded with bit 255 masked, and values from p to 2^255 - 1 are accepted and reduced (section 5: "implementations MUST accept non-canonical values").
  • shared_secret refuses the all-zero output with errc::small_order (the check section 6.1 describes): the peer's key had small order, so the result is independent of the secret. scalar_mult makes no such check.
  • Public keys on the twist are not rejected (X25519 is twist-secure); Wycheproof marks those "acceptable".
Relationships
  • curve25519/field.hpp: the arithmetic; curve25519/ed25519.hpp: signatures on the same curve.

Implementations and variants

One: the Montgomery ladder of RFC 7748, section 5, with a constant-time conditional swap per bit and one inversion at the end.

Guarantees and contracts
  • scalar_mult, public_key_from_secret, shared_secret, clamp: constant time in the secret (255 ladder steps whatever its value; swaps are masked); the u-coordinate is public. The all-zero check reveals only that the output is zero, which the error reports anyway.
  • The shared secret is returned in secret_bytes<32>; intermediates are wiped.
  • Everything is constexpr and noexcept; no allocation.
Errors

shared_secret returns errc::small_order for the all-zero shared secret.

Examples
namespace x25519 = snicholls::crypto::x25519;
// Secrets come from a CSPRNG or a KDF; these are RFC 7748's published test secrets
const secret_bytes<32> alice(hex<32>("77076d0a7318a57d3c16c17251b26645df4c2f87ebc0992ab177fba51db92c2a"));
const secret_bytes<32> bob(hex<32>("5dab087e624a8a4b79e17f8b83800ee66f3bb1292618b6fd1c2f8b27ff88e0eb"));
const x25519::public_key alice_pub = x25519::public_key_from_secret(alice);
const x25519::public_key bob_pub = x25519::public_key_from_secret(bob);
auto k_alice = x25519::shared_secret(alice, bob_pub); // result<secret_bytes<32>, errc>
auto k_bob = x25519::shared_secret(bob, alice_pub);
const auto refused = x25519::shared_secret(alice, x25519::public_key{}); // u = 0: errc::small_order

Known issues and gotchas

The shared secret is not uniformly random: hash it (HKDF) before using it as a key, and bind both public keys into that derivation if the protocol needs it.
