Detailed Description

BIP-32 hierarchical deterministic keys over secp256k1: the master key from a seed, private and public child derivation, fingerprints, and the xprv / xpub serialisation (with its tprv, yprv, zprv cousins).

Overview
  • extended_private_key::from_seed(seed): the master key, HMAC-SHA512 keyed by "Bitcoin seed".
  • derive_child(i) / derive(path): CKDpriv for hardened (i >= 2^31) and non-hardened indices; on an extended_public_key, CKDpub for non-hardened indices only.
  • public_key(): the extended public key (the "neutered" key).
  • fingerprint() / identifier(): HASH160 of the compressed public key, and its first four bytes.
  • serialize(version) / to_text(versions) / parse(text, versions): the 78-byte serialisation and its base58check text (address/base58check.hpp), with the versions of BIP-32 (xprv / xpub, tprv / tpub), BIP-49 (yprv / ypub) and BIP-84 (zprv / zpub).
Relationships
  • bip39/mnemonic.hpp: where the seed usually comes from; hd/path.hpp: the paths; hd/slip10.hpp: the Ed25519 counterpart; secp256k1/ecdsa.hpp: what the derived keys sign with.
  • Group: Wallets.
Implementations and variants

One.

Guarantees and contracts
  • Private derivation is constant time in the key, the chain code and the seed: the HMAC has no data-dependent branch, the parent's public key (for a non-hardened child and for the fingerprint) is the constant-time mul_base, and the range check of I_L and the sum are masked. The only branch is on the validity of the child (probability below 2^-127), which BIP-32 makes public anyway: the caller moves to the next index.
  • Public derivation (extended_public_key) and parse handle public data and may be variable time. An xprv's text holds the key: parse of one runs the base58 decoder, which is not constant time (see "Known issues").
  • Private keys and chain codes are wiped (secret_bytes); extended_private_key is move-only, clone() copies.
  • constexpr and noexcept throughout; no allocation.
Errors

errc::invalid_seed for a seed outside 16 to 64 bytes; errc::invalid_derivation when I_L is at or above n or the child key is zero (or the identity), as BIP-32 specifies, for which the caller uses the next index; errc::hardened_required for a hardened index from a public key; errc::invalid_extended_key for a serialisation with an unknown or mismatched version, bad key data, a zero depth with a parent or an index, or a key out of range; errc::invalid_checksum, errc::invalid_character, errc::invalid_length from the base58check text.

Examples
const auto seed = snicholls::crypto::test::hex<16>("000102030405060708090a0b0c0d0e0f"); // BIP-32 vector 1
const auto master = extended_private_key::from_seed(seed);
if (!master)
return 1;
const auto path = derivation_path::parse("m/0'/1/2'").unwrap();
const auto node = master->derive(path); // CKDpriv, constant time
auto xprv = node->to_text(); // key material: wiped below
const auto xpub = node->public_key().to_text(); // public: share it
const auto watched = node->public_key().derive_child(2); // CKDpub: an xpub derives its non-hardened children
const auto refused = node->public_key().derive_child(hardened(2)); // but never a hardened one
const auto back = extended_public_key::parse(std::string_view(xpub.data(), xpub.size()));
Performance

benchmarks/hd/bip32_benchmark.cpp: one constant-time multiplication per derivation step (two for a non-hardened one) dominates; see README.md for numbers.

Tests and demos

tests/hd/bip32_test.cpp: BIP-32 test vectors 1 to 4 (every chain, xpub and xprv both ways, private and, where the path allows, public derivation) and all sixteen invalid keys of vector 5; SLIP-10's secp256k1 vectors (fingerprints, chain codes, keys); Trezor's BIP-39 master keys. demos/hd/bip32_demo.cpp.

Dependencies

<array>, <cstdint>, <span>; core's result.hpp; the library's HMAC-SHA512, HASH160 and base58check.

Known issues and gotchas

The base58 decoder is variable time, so decoding an xprv can leak through timing something about the key's text to an observer who can time that one call; keep xprv text off paths an attacker can time, or store the 78 bytes (serialize) instead. The text returned by to_text for a private key is key material: wipe it (secure_wipe) when done.
