Detailed Description

Which version of snicholls-crypto you are compiling against.

CMake knows the version and exports it for find_package, but a header-only library is also consumed by people who copy the headers into a tree with no build system at all, and they have no CMake to ask. Without these macros there is no way for them to find out what they have, or to write code that works against two versions:

#if SNICHOLLS_CRYPTO_VERSION >= SNICHOLLS_CRYPTO_VERSION_CHECK(0, 2, 0)
// use something that only exists from 0.2 onwards
#endif

A consumer that needs a minimum says so once, where the compiler can see it:

SNICHOLLS_CRYPTO_REQUIRE_VERSION(0, 1, 0);
SNICHOLLS_CRYPTO_REQUIRE_VERSION
#define SNICHOLLS_CRYPTO_REQUIRE_VERSION(major, minor, patch)
Fail to compile unless snicholls-crypto is at least major.minor.patch.

That is the compile-time half of the diamond rules in CMakeLists.txt; the CMake half is snicholls_crypto_require(x.y.z). The number here, the project(... VERSION) in CMakeLists.txt and the release tag are three copies of one fact, checked against each other by scripts/check_version.py on every CI job. Three places holding one number is exactly how a number goes quietly wrong.

SNICHOLLS_CRYPTO_REQUIRE_VERSION(0, 1, 0); // stops the build against anything older

std::printf("snicholls-crypto %s (encoded %d)\n", SNICHOLLS_CRYPTO_VERSION_STRING, snicholls::crypto::version());
#if SNICHOLLS_CRYPTO_VERSION >= SNICHOLLS_CRYPTO_VERSION_CHECK(0, 1, 0)

#endif
