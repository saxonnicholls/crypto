Detailed Description

ECDSA on P-384 with SHA-384 (JOSE's ES384, TLS 1.3's ecdsa_secp384r1_sha384, X.509's ecdsa-with-SHA384): keys, verification, JOSE and DER forms.

Overview
  • private_key (48 bytes, 1 to n - 1) and its public_key (SEC1 compressed, 49 bytes, or uncompressed, 97), computed in constant time.
  • verify(key, hash, signature): FIPS 186-5 / SEC 1 verification over a 48-byte SHA-384 hash, either s accepted; verify_message hashes the message with SHA-384 first.
  • signature::from_jose / JOSE: JWS's 96-byte r || s (TLS and X.509 use DER); from_der / der(): strict DER.

Verification only: there is no P-384 signing here (P-256 and Ed25519 sign). With P-384's 384-bit order the SHA-384 hash is used whole, reduced modulo n.

Relationships
  • p384/point.hpp, p384/scalar.hpp; detail/ecdsa_der.hpp (the DER shared with P-256 and secp256k1); p384/ecdh.hpp (key agreement with the same keys).
  • Group: P-384.
Implementations and variants

One: d G in constant time (point::mul); verification with point::mul_add_public in variable time.

Guarantees and contracts
  • private_key and public_key(): constant time in the private key. Revealed on purpose (ct::declassify): whether a key's bytes are in range. The key is held in secret_bytes<48>; intermediates are wiped.
  • verify, verify_message, public_key::parse, signature::from_der: variable time; public data only.
  • constexpr, noexcept, no allocation.
Errors

errc::invalid_private_key for a key of 0 or at least n; errc::invalid_public_key for an encoding that is not SEC1 compressed or uncompressed of a point on the curve; errc::invalid_signature for r or s outside 1 to n - 1, DER that is not DER, or a signature that does not verify.

Examples
namespace p384 = snicholls::crypto::p384;
// RFC 6979's published test key and signature; a real key comes from a CSPRNG
const auto key = p384::private_key::from_bytes(
hex<48>("6b9d3dad2e1b8c1c05b19875b6659f4de23c3b667bf297ba9aa47740787137d896d5724e4c70a825f872c9ea60d2edf5")).unwrap();
const p384::public_key pub = key.public_key();
const p384::signature sig{hex<48>("94edbb92a5ecb8aad4736e56c691916b3f88140666ce9fa73d64c4ea95ad133c81a648152e44acf96e36dd1e80fabe46"),
hex<48>("99ef4aeb15f178cea1fe40db2603138f130e740a19624526203b6351d0a3a94fa329c145786e679e7b82c71a38628ac8")};
const auto ok = p384::verify_message(pub, bytes("sample"), p384::signature::from_jose(sig.jose())); // ES384: r || s
const auto der = sig.der(); // TLS, X.509
const auto from_der = p384::signature::from_der(std::span<const std::uint8_t>(der.data(), der.size()));
const auto wrong = p384::verify_message(pub, bytes("other"), sig); // errc::invalid_signature

Dependencies

<array>, <cstdint>, <span>; core's result.hpp and SHA-384.

Known issues and gotchas

Hash the message first for verify (48 bytes of SHA-384), or call verify_message. JOSE's signature is r || s, never DER; TLS's and X.509's are DER.

Status
