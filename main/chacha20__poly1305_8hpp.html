Detailed Description

ChaCha20-Poly1305 (RFC 8439) and XChaCha20-Poly1305: authenticated encryption with associated data.

Overview

Encrypts and authenticates a message under a 32-byte key and a nonce, and authenticates associated data (a header, a cookie's name, a record id) that is not encrypted. seal writes the ciphertext, as long as the plaintext, and returns the 16-byte tag; open checks the tag in constant time and only then writes the plaintext.

  • chacha20_poly1305_seal / _open: RFC 8439, a 12-byte nonce. A nonce must never repeat under one key: use a counter, or XChaCha20.
  • xchacha20_poly1305_seal / _open: draft-irtf-cfrg-xchacha, a 24-byte nonce, long enough to choose at random for every message (session cookies, tokens at rest). HChaCha20 derives a subkey from the key and the first 16 nonce bytes; the last 8 make the 12-byte nonce, after four zero bytes.

Implementations and variants

One: RFC 8439 section 2.8, the Poly1305 key the first 32 bytes of the ChaCha20 block at counter 0, the message encrypted from counter 1, the tag over aad || pad16 || ciphertext || pad16 || len(aad) || len(ciphertext).

Guarantees and contracts
  • Constant time in the key, the plaintext and the tag: ChaCha20 is additions, rotations and XORs; Poly1305's reduction is masked; the tag is compared in full with no early exit. Lengths and the nonce are public. Revealed on purpose (ct::declassify): whether the tag matched.
  • open writes nothing it has not authenticated: on a mismatch the output is zeroed and errc::authentication_failed returned. Intermediate keys and keystream are wiped.
  • The input and output may be the same span (in place); otherwise they must not overlap.
  • constexpr, noexcept, no allocation.
Errors

errc::invalid_length when the output is not exactly as long as the input, or the message is longer than RFC 8439 allows (2^38 - 64 bytes); errc::authentication_failed from open when the tag does not match.

Examples
namespace aead = snicholls::crypto::aead;
// A test key; a real one comes from a CSPRNG or from core's hkdf over a master secret
const auto key = hex<32>("808182838485868788898a8b8c8d8e8f909192939495969798999a9b9c9d9e9f");
const auto nonce = hex<24>("404142434445464748494a4b4c4d4e4f5051525354555657"); // random per cookie
const auto name = bytes("session"); // authenticated, not secret
const auto value = bytes("{\"user\":42,\"exp\":1795000000}");
std::vector<std::uint8_t> sealed(value.size());
const aead::tag tag = aead::xchacha20_poly1305_seal(key, nonce, name, value, sealed).unwrap();
std::vector<std::uint8_t> opened(sealed.size());
const auto ok = aead::xchacha20_poly1305_open(key, nonce, name, sealed, tag, opened);
auto tampered = sealed;
tampered[0] ^= 1;
const auto refused = aead::xchacha20_poly1305_open(key, nonce, name, tampered, tag, opened); // authentication_failed

Known issues and gotchas

Never reuse a nonce under the same key: with ChaCha20-Poly1305 a repeat reveals the XOR of two plaintexts and lets an attacker forge tags. With random nonces use XChaCha20-Poly1305. The tag authenticates the associated data but does not hide it.
